OpenMausBot fork · Architecture and contribution plan

Generative UI without a cloud control plane.

A private MCP tool surface lets only OpenMaus bots ask for typed components. The harness validates and persists those calls, React renders them from SQLite, and Electron owns trusted human actions such as completing a Todoist task.

The core idea

One registry, three execution planes.

The model plane chooses a component. The server plane validates, enriches, authorizes, and stores it. The renderer plane displays it. Interactive writes cross a separate Electron-only boundary, so a transcript never becomes a capability.

Adding a presentational component should be one registry row, one renderer, and tests. Adding an action also needs a trusted handler and an action-event contract.
OpenMaus botSees private ui MCP tools plus a system primer generated from the registry.
UI MCP proxyRuns over stdio inside the provider turn and posts through a boot-scoped private token.
Harness serverValidates, enriches, correlates provider identity, persists to SQLite, and broadcasts.
React + ElectronReplays the component. Browser is read-only; Electron owns trusted action IPC.

02

The complete show path

The component is not HTML emitted by the model. The model chooses a registered tool and supplies JSON. Every later step is deterministic application code.

The bot is told what exists

Only when integrations.ui is mounted, OpenMaus adds a system primer generated from GALLERY. Tool schemas remain authoritative. Adding a registry row updates both the actual MCP tool list and the bot primer.

The provider calls one UI tool

The provider process invokes mcp__ui__show_* over stdio. No UI MCP server is registered in the user's global Claude, Codex, or system configuration.

The proxy proves ownership

The proxy receives a boot-scoped token plus exact bot and thread IDs. The internal route rejects an unknown bot or a thread that bot does not own.

The server validates and enriches

Presentational calls validate directly. Todoist calls accept exact task IDs, then the server loads title, description, due date, project, labels, and completion state using its private token.

One public envelope is persisted

SQLite stores callId, component name, bounded arguments, human-readable result, status, and provider origin. It deliberately stores no completion token.

React revalidates and renders

The renderer parses the same bounded shape again, selects a compiled component, and wraps every branch in an error boundary. Restart simply replays the stored envelope.

Provider CLI
  └─ stdio MCP: show_todoist_tasks({ taskIds })
       └─ private POST /api/internal/ui/show
            ├─ exact bot/thread ownership
            ├─ gallery schema + size bounds
            ├─ Todoist GET task + project metadata
            ├─ SQLite ComponentCall
            └─ EventBus → /api/bots + renderer

Browser renderer: can inspect, cannot mutate
Electron renderer: click → preload IPC → Electron main → read-only authorize
                                            → Todoist close
                                            → trusted receipt
                                            → server reconcile
03

Why only OpenMaus bots know these tools

The UI capability is born inside an OpenMaus turn. It is not installed globally and it is not exposed to unrelated local agents.

Capability-gated mount

The harness checks the selected OpenMaus provider adapter for uiMcp: true. Only then does it create integrations.ui.

Private per-turn process

The MCP proxy is a child of the provider turn. It receives only the harness URL, bot ID, thread ID, provider identity, and a fresh boot token.

Registry-derived primer

The model prompt is generated from the same registry that generates the MCP tools. New components cannot exist in one surface and be forgotten in the other.

Reliability claim: OpenMaus bots receive the tools and primer in both one-to-one and room turns. Other Claude Code sessions do not, because no global MCP or skill registration is created.

How to add another component

Presentational components stay cheap. Interactive components pay for a separate action protocol instead of smuggling capabilities into model output.

StepPresentational componentInteractive component
1. RegistryAdd one GallerySpec with name, schema, description, and confirmation.Same, plus declared action names and user-visible verbs.
2. Server resolverOptional, only if trusted data replaces model arguments.Required. Resolve candidate state and authorize exact entity/action pairs.
3. RendererAdd one bounded React component and register its name.Add controls that call preload IPC, never a public mutation endpoint.
4. Trusted actionNone.Electron handler, one-time gate, remote write, receipt, reconciliation.
5. PersistenceStore the public component envelope.Store public state and action events; never store the write capability.
6. TestsSchema, bounds, malformed replay, visual render.All presentational tests plus bypass, concurrency, duplicate, failure, restart, and accessibility tests.

Good next component

Decision card: options, evidence, recommendation, and one human choice. The action stays local to OpenMaus state unless an explicit adapter writes elsewhere.

Good next component

Calendar proposal: events and conflicts rendered read-only first, with a separate Electron action to create the exact approved batch.

Good next component

Ops finding: severity, evidence, status, and prepared fix. No action handler unless the fix boundary is separately designed.

06

Action feedback: the missing loop

Today the card updates deterministically, but the provider session is not reliably informed that the person acted. That is why a follow-up such as “how about now” can trigger a redundant Todoist query. The fix should be a general component-action protocol, not a Todoist-only prompt.

Proposed durable event

Persist a ComponentActionEvent beside the component:

  • actionId and idempotency key
  • threadId, callId, component and action names
  • public entity label and bounded result
  • status: started, succeeded, failed
  • trusted origin: Electron main
  • provider-context delivery cursor

Proposed bot awareness

  1. Electron succeeds and writes its trusted receipt.
  2. Server reconciles component state and appends the action event.
  3. The chat shows a deterministic “Completed in Todoist” activity immediately.
  4. The next provider turn automatically receives every unread action event in a system-owned context block, even when resuming a provider cursor.
  5. Optional per-bot policy can start a tiny tool-disabled acknowledgment turn immediately.
Human click
  → Electron main closes remote task exactly once
  → trusted ComponentActionEvent persisted
  → component updates immediately
  → visible OpenMaus activity: "Completed in Todoist"
  → unread event added to bot context cursor
  → next bot turn already knows; no Bash/curl re-check

Optional immediate acknowledgment turn:
  automationSource = "ui_action"
  tools = disabled
  purpose = acknowledge or update plan only
  no duplicate remote action
Recommendation: ship durable context delivery first. Add automatic model acknowledgments only as an opt-in policy, because they consume tokens and can create noise. The deterministic activity plus next-turn context solves the reliability problem without another autonomous actor.

What servers are actually required

Development uses three visible processes because Vite is separate. A packaged desktop build collapses that topology.

Development

  • Harness server on 18879
  • Webhook receiver on 18880
  • Vite renderer on 5199
  • Electron desktop window
  • Provider CLI child per active bot turn
  • UI MCP proxy child per supported provider turn

Packaged application

  • Electron main process
  • Bundled harness server as an Electron utility process
  • Compiled renderer assets served by the harness
  • SQLite and encrypted credentials on the local machine
  • No Vite server
  • No hosted generative-UI service
External dependencies: the chosen model provider still receives model turns, and Todoist receives task reads/writes. The UI protocol, persistence, rendering, and action boundary remain local.
08

How this becomes an upstream open-source contribution

The current fork proves the whole vertical slice. An upstreamable series should separate the general protocol from the Todoist opinion.

PR 1: component protocol and compiled gallery

Land ComponentCall, bounds, SQLite replay, exact tool classification, renderer boundary, record/metrics/checklist/quote, and evidence tests. No external credentials or actions.

PR 2: provider-neutral private MCP mount

Land the UI proxy and shared integration contract across Claude, Codex, ACP, Antigravity, and Box. Include the registry-derived system primer and prove no global MCP registration.

PR 3: generic trusted action protocol

Introduce Electron-only actions, one-time gates, receipts, reconciliation, component-action events, and provider-context delivery without naming Todoist.

PR 4: Todoist adapter

Add encrypted credentials, recorded fixtures, task/project enrichment, native task renderer, close action, and end-to-end evidence as an example integration.

Contribution hygiene

Add an ADR for the public component envelope and action boundary. Keep every external service behind an adapter and fixture corpus.

Repository quality

Add a committed render command, CI evidence artifact, and objective STANDARDS.md rules for interactive components.

Maintainer choice

Todoist can stay optional. The core contribution is the protocol, private MCP mount, persistence, renderer registry, and trusted local action seam.
