A standalone repository wins over living inside either host because neither application should own the other’s dependency. One package version wins over several packages because schemas, renderers, and compilers must advance together. Apache-2.0 preserves the license and attribution of the OpenMausBot source being extracted while remaining consumable by MIT OpenBot. GitHub tags provide reviewable pinned inputs now; npm publication waits until both host targets prove stable.

The first release, v0.1.0, covers Record, Metrics, Checklist, and Quote because they prove rendering without host actions against stock OpenBot. Todoist is built in the same task but crosses a separate release gate: the secure component-function and review/apply seam currently exists only on the divergent local setup/local branch, not on CopilotKit/openbot upstream. This task therefore ports the minimum secure seam onto current upstream commit 6826e11afd52f03c30af2d873203792acad95f63 as a PR-ready branch. Todoist enters a later pack tag only after that upstream seam is available from a public commit. OpenMausBot can consume v0.1.0 immediately without creating or depending on an OpenBot fork.

The pack owns meaning; hosts own authority

The shared boundary is deliberately narrower than either application. It owns what a component is and how it renders. It does not decide who may call it, where data comes from, how a conversation persists, or which trusted process performs an action. In the diagram, GALLERY is OpenBot’s compiled component catalogue; GallerySpec is OpenMausBot’s server tool record; governed functions are OpenBot server calls allowed by deployment policy; and private MCP is OpenMausBot’s per-turn Model Context Protocol tool transport.

The contract separates what the model sends from what the screen shows

A host tool’s input is not necessarily the component’s renderable view. A resolved view is validated, display-ready data after a host has loaded or enriched trusted facts. Todoist proves the distinction: OpenMaus receives exact task IDs and resolves trusted tasks on the server; OpenBot receives a filter, project, and limit, then its renderer loads tasks through the governed todoistRead function. Both render one canonical view without sharing their data-access path.

The shared renderer is presentation-only. A host controller resolves data, chooses effective completion state, owns async row state, and passes a per-call dispatch closure. OpenBot’s controller runs todoistRead on mount, lets local post-action state win, and dispatches through the existing todoistTaskReview → short-lived token → todoistTaskApply sequence. OpenMausBot resolves once on the trusted server, persists authorization-bearing recurring, shown due date, and unavailable fields, lets patched server view state win, and constructs dispatch per {threadId, callId}; those correlation values never come from renderer action payloads. The compiler emits the host tool name—not the canonical ID—into every OpenBot route, GALLERY record, governed-function call, and exact reads() list.

Exactly what is shared

AG-UI is OpenBot’s agent-to-application event protocol; CopilotKit Intelligence is its conversation service. A ComponentCall is OpenMausBot’s persisted component message, including arguments and provider origin. These host contracts remain outside the pack.

Where the code lives, and what gets generated

New repository: mimen/generative-ui-pack

One root package exports ./core, ./react, ./compiler, ./openbot, and ./openmaus. A compatibility manifest records the package version, generated-file format, and exact host commit supported by each compiler target. Tagged releases include built JavaScript, declarations, and CSS so Git consumers execute no lifecycle build. Tags are append-only release inputs: the release workflow refuses an existing version and both host manifests record the tag’s commit SHA. Public npm publication waits until both adapters have survived real use.

OpenBot upstream seam and overlay

Stock compatibility targets public upstream commit 6826e11afd52f03c30af2d873203792acad95f63. Before Todoist can be claimed compatible, a PR-ready upstream branch ports only the minimum component-function contract, external-actor checks, review-token machinery, Todoist read/review/apply functions, routes, database wiring, and tests from the divergent local branch. Calendar and Todoist-triage features are excluded. Until that seam is publicly reachable, public package CI and released manifests cover only the four read-only components.

The compiler overlay is a name-level, contract-versioned patch. It adds the pack at an exact Git commit SHA to app/package.json, regenerates and verifies bun.lock, imports compiled pack CSS, and replaces only the definitions owned by the pack. For mixed modules such as cards.tsx, a source-hash-guarded unified patch swaps Record, Metrics, and Checklist exports/bindings to package imports while preserving showNotice and every unowned declaration. The patch manifest records the expected source hash, exact changed ranges, generated files, owned names, and retained names.

Verification asserts that every pre-overlay component name still exists afterward unless explicitly retired, every name is unique, and the OpenBot tool input schemas for existing names remain JSON-schema compatible with the pinned baseline. This preserves governance rows and avoids both duplicate registration and accidental loss of an unowned component.

A disposable checkout receives only the declared overlay patch, then performs a clean install, typecheck, tests, production build, and gallery capture. The verifier rejects changes outside the manifest and confirms the installed pack SHA. A later upstream commit requires a newly tested compatibility entry rather than silently retargeting an old one.

OpenMausBot integration

OpenMausBot replaces four read-only renderers first, then Todoist after the upstream seam gate. New calls add top-level componentId and viewVersion fields beside the existing host tool name; both strict current and legacy stored-call schemas explicitly accept those optional fields, while new writers require them. They never enter component arguments. The stored-call parser maps known legacy names to version 1, retains arguments unchanged, and keeps a decoder for each persisted view version. Unknown names keep the existing fallback.

The OpenMaus Todoist persisted schema extends the common visual task with required authorization metadata: recurring, nullable shown due date, and unavailable. The resolver must supply those fields; no security-relevant default is permitted. Replay/action tests cover unavailable rows and recurring tasks whose live due date advanced after the shown occurrence. Candidate integration pins an exact pack SHA; after tagging the unchanged commit, OpenMaus switches to the tag, verifies tag-to-SHA identity, regenerates its lockfile, and reruns install, replay, actions, build, and gallery evidence.

Migration sequence

Establish the package and compiler contracts

Create the standalone Apache-2.0 repository, strict build, one-package exports, compiled CSS, deterministic fixtures, host-kind mappings, replacement-patch manifest, compatibility manifest, and candidate-SHA verification command.

Ship the read-only path first

Extract Record, Metrics, Checklist, and Quote. Generate replacement bindings against public OpenBot upstream and OpenMausBot, test one candidate SHA in both hosts, tag that unchanged commit as v0.1.0, verify tag identity, rerun tag-based tests, and land the OpenMaus read-only migration.

Port the minimum secure Todoist seam onto upstream

Create an isolated branch from current CopilotKit/openbot upstream. Port component-function authorization, external-actor enforcement, review tokens, Todoist read/review/apply, routing, audit, and tests without Calendar or triage. Produce a PR-ready diff and verification evidence; do not post externally without the outbound approval surface.

Extract Todoist as view plus host controllers

Share the visual schema, fixture, and presentation component. OpenBot’s controller owns mount-time reads, local completion precedence, and review/apply dispatch. OpenMausBot’s controller owns server-view precedence and a per-ComponentCall dispatch closure; server-only resolution never enters the renderer bundle.

Add versioned OpenMaus persistence

Extend strict stored-call schemas with top-level canonical ID/version fields, legacy alias inference, retained decoders, and required OpenMaus authorization metadata. Verify old rows, new rows, unknown names, unavailable tasks, recurring occurrence changes, recovery, and pending reconciliation.

Release Todoist only from a public OpenBot base

Once the secure seam is reachable from an upstream or public PR commit, add that commit to the compatibility manifest. Test a new pack candidate SHA against both hosts, tag the unchanged commit as the next release, verify tag identity, rerun both host suites, and then land OpenMaus Todoist migration.

Failure modes the implementation must close

A private fork is mistaken for upstream

Released manifests reference only publicly fetchable commits. The local setup/local branch is evidence for the port, never a public compatibility baseline.

Generated bindings duplicate or erase host components

Source-hash-guarded name-level patches replace only owned definitions, retain every unowned name such as showNotice, and assert pre/post name preservation plus uniqueness.

One completion policy lies in one host

Host controllers compute presented task state: OpenBot local action state wins; OpenMaus patched server state wins. The shared renderer receives already-reconciled rows.

Resolution crosses a trust boundary

ResolvePort and renderer-side DispatchPort are separate types. OpenMaus server resolution cannot be instantiated or bundled in the browser.

Actions address another transcript call

OpenMaus dispatch is constructed per {threadId, callId}; renderer actions carry only task/action intent and cannot choose correlation identifiers.

Canonical IDs bypass OpenBot grants

Generated OpenBot network calls always use the existing host tool name and exact function list. The compiler asserts route, catalogue name, and grant keys agree.

Strict stored schemas quarantine new rows

Canonical ID/version fields are top-level and explicitly accepted by both current and legacy stored-call schemas. Replay tests cover both parse paths.

Security metadata is defaulted away

The OpenMaus resolver must provide recurring, shown due, and unavailable fields. Missing fields fail closed before persistence or dispatch.

OpenBot’s contract drifts

Each compiler target names a public commit and checks required files, symbols, kinds, and generated patch paths. Unknown contracts fail closed.

Framework or style duplication enters a host

React, React DOM, and Zod are peer dependencies; the pack ships compiled CSS variables rather than requiring host Tailwind scanning.

Generated code becomes a second source

Generated files contain adapter glue only, replace declared outputs wholesale, and are byte-stable in CI.

License provenance is blurred

The pack remains Apache-2.0 with attribution for extracted OpenMausBot code.

  • v0.1.0 shares Record, Metrics, Checklist, and Quote with no duplicate renderer implementation.
  • Stock OpenBot at public commit 6826e11 builds from untouched source plus a replacement overlay containing the exact pack dependency, lockfile, CSS, and unique generated bindings.
  • OpenMausBot lands the four read-only components from the same tag and replays existing messages unchanged.
  • The public Apache-2.0 repository and append-only v0.1.0 tag resolve to the commit tested in both hosts.
  • A PR-ready OpenBot branch ports the minimum secure Todoist function seam onto current upstream without Calendar or triage scope.
  • The shared Todoist view and host controllers preserve OpenBot review-token/apply stale-state protection and OpenMaus server enrichment, correlation, recovery, and Electron authorization.
  • OpenMaus new-format calls store top-level canonical ID/version fields; strict current and legacy schemas parse them, and old snake-case rows infer version 1.
  • Todoist tests cover unavailable rows, recurring occurrence changes, pending reconciliation, local-wins OpenBot state, and server-view-wins OpenMaus state.
  • Preview actions are disabled; detail headings, lists, values, and statuses remain in the accessibility tree.
  • Every target rejects unsupported source hashes, duplicate names, missing pre-overlay names, incompatible existing tool schemas, undeclared patch ranges, and non-deterministic output.

Also deferred: public npm, an A2UI declarative-UI compiler target, and runtime installation into an already-built OpenBot image.

What actually shipped

Released. mimen/generative-ui-pack is public, Apache-2.0, and tagged v0.1.0 resolving to f44dfb7. Record, Metrics, Checklist, and Quote are shared. OpenMausBot landed the migration on main at 35c5364, with the four model-facing tool contracts proven byte-identical to the previous build and new calls persisting an additive canonical id and view version. Stock OpenBot at public 6826e11a builds, typechecks, lints, passes its 116 application tests, and renders the shared components through a generated native GALLERY overlay applied inside a disposable clone.

Where the build diverged. Three things changed under review. The pinned OpenBot baseline moved from a commit that existed only on a local branch to genuine public upstream, which also forced Todoist out of the first release. The overlay’s in-place transaction layer—locks, journals, staged rollback, crash recovery—was deleted rather than hardened after independent review demonstrated a working write-outside-checkout escape and then a lock-ownership race; the compiler is now pure and only a compiler-owned temporary clone is ever mutated, which removed the entire vulnerability class. And the overlay now pins a release tag instead of a baked self-referencing commit and lockfile, because a commit cannot contain its own hash.

Risks that were real. The plan’s worry about preserving unowned host components was justified: OpenBot’s cards.tsx also exports showNotice, so module-level replacement would have silently deleted a component whose publication and grant rows live in the deployment database. Name-level patching plus a pre/post name-preservation assertion closed it. The Todoist authorization worry was also justified—the first port would have bypassed the review-token and stale-state checks entirely.

Still gated. Todoist is not in v0.1.0. Its secure component-function seam is ported onto current upstream and verified locally at 34d56d9, but pushing to CopilotKit/openbot returned 403, so no public commit exists to compile against. Sharing the Todoist view stays blocked on that seam becoming publicly reachable.
